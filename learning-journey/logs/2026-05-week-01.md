## QA Reflection: Documenting Before Fixing

This week, I practiced writing a QA bug report before fixing the issue. The bug was small: two GitHub links on the portfolio homepage pointed to an outdated repository path.

Writing the report first helped me slow down and explain the problem clearly. I had to name what was wrong, where it happened, what I expected, what actually happened, and how it could affect a visitor. That made the fix feel more intentional instead of just changing a link and moving on.

I also learned that QA is not only about finding mistakes. It is about making issues understandable enough that someone else could reproduce them, prioritize them, and fix them with confidence. That feels useful for games too, because clear bug reports help teams understand what a player or tester experienced.

## Project Reflection: Building qa-bug-report-tool

This week, I also built the first version of `qa-bug-report-tool`, a small Python command-line project that turns rough QA notes into structured Markdown bug reports.

The biggest Python lesson was seeing how a CLI can connect small pieces: reading text input, parsing labels, storing the result in a simple data model, and printing or saving Markdown output. I also practiced keeping the project structure readable with `src/`, `tests/`, `sample-data/`, `reports/`, and `examples/`.

Pytest helped me think about behavior instead of only looking at the code. The tests check normal parsing, rough notes, batch conversion, Markdown formatting, help text, and validation warnings. That made the tool feel less like a one-time script and more like something I can safely improve later.

Writing the README was part of the learning too. I had to explain what the tool does, how to run it, what the sample data means, and how AI assistance was used. I want the project to be portfolio-ready without pretending I already know everything. The responsible AI section matters because it keeps the work honest: AI helped with planning, drafting, edge cases, and tests, while I am still practicing how to read, understand, and maintain the code.

## Project Reflection: Building the Obsidian Conversation Sync Agent

This week, I built the first version of `obsidian-conversation-sync-agent`, a small local Python command-line tool that turns exported AI conversations into Obsidian-friendly Markdown notes.

The tool reads local `.json`, `.md`, and `.txt` files, parses conversation content, and writes notes into an Obsidian vault folder. It also creates an `AI Conversation Index.md` note and puts synced conversations into a `Conversations/` folder so the vault feels more readable and connected. Each generated note has a human-review reminder, a summary placeholder, follow-up checkboxes, and sections for useful takeaways, decisions, commands, prompts, and related links.

What it does not do yet is just as important. It does not log into ChatGPT, Codex, Discord, Slack, or any private account. It does not automatically summarize conversations with another AI model. It also does not decide which notes are safe or useful enough to share publicly. The first version starts with exported files that I control, and the notes are clearly marked as needing review.

The Python practice here felt different from the QA bug report tool. I worked with folders, paths, JSON shapes, file writing, dataclasses, command line arguments, Markdown rendering, and sync state. I also practiced writing tests for behavior that touches the filesystem, like making sure a dry run does not write files and making sure unchanged conversations are skipped after they are already synced.

The confusing part was understanding the shape of conversation exports. A plain text file is simple, but a ChatGPT-style export can have nested message data, roles, timestamps, and content parts. I also had to think about Obsidian as more than a folder of Markdown files. If the output is hard to browse, then the sync technically works but the documentation habit still suffers.

Syncing AI conversations into Obsidian supports my learning-in-public workflow because useful explanations, project decisions, and next-step prompts can become reviewable notes instead of disappearing into chat history. The goal is not to pretend the AI conversation is finished documentation. The goal is to create an inbox where I can review what happened, pull out what I actually understand, connect it to a project or learning log, and remove anything private before it ever becomes public.

This project also connects back to games in a practical way. Game work depends on readable notes, clear follow-up, and being able to trace why a decision was made. This tool is not a game project, but it helps build the documentation habits I would want around game-inspired projects later.
