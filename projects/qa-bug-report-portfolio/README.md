# QA Bug Report Portfolio

## Status

Planned / in progress.

## Goal

Practice writing clear, beginner-friendly bug reports by documenting issues in websites, tools, simple web projects, or game-inspired practice builds.

This project is not here to claim professional QA experience. It is here to build the habit of observing carefully, explaining problems clearly, and documenting enough detail that someone else could understand what happened.

## Why I Chose It

Games are one reason I am interested in software. Game experiences depend on systems, feedback, UI, flow, and small details working together. A QA bug report portfolio gives me a practical way to practice noticing those details without jumping into a full game project too early.

It also connects directly to rebuilding through documentation: each report is a small exercise in clarity, patience, and structured thinking.

## Skills Practiced

- Writing clear titles and summaries
- Describing expected behavior and actual behavior
- Listing steps to reproduce an issue
- Noting environment details, such as browser, device, or page
- Organizing screenshots or supporting notes
- Reflecting on what made the issue confusing
- Using GitHub folders and Markdown to keep reports readable

## Suggested Files

- `README.md` for the project overview
- `bug-report-template.md` for a reusable report format
- `reports/README.md` for the report archive
- Future files like `reports/001-example-report.md`
- Optional future screenshots folder if a report needs images

## Definition of Done

This starter project is done when:

- The project folder has a clear README.
- A reusable bug report template exists.
- The reports folder explains how future reports will be organized.
- At least one real practice bug report is added later.
- The writeup stays honest about this being practice, not professional QA work.

## How I Will Write Reports

Each report should include:

- Title
- Severity
- Priority
- Environment
- Steps to reproduce
- Expected result
- Actual result
- Impact
- Notes

## Reflection Questions

- Was the issue easy to describe clearly?
- Did I include enough detail for someone else to reproduce it?
- What information did I forget at first?
- How does this connect to games, player experience, or software quality?
- What would make the next report clearer?

## Next Steps

- Use the bug report template for the first real practice report.
- Start with a small website or one of my own portfolio pages.
- Keep reports simple and specific.
- Add screenshots only when they help explain the issue.
